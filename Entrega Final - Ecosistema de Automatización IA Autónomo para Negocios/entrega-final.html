Proyecto final · Automatización con IA

Ecosistema de automatización
para Arrecife

Un restaurante de La Paloma recibe pedidos y reservas por su web. El sistema los valida, los razona contra las políticas del local con un modelo de lenguaje, los registra en Notion y avisa al dueño — deteniéndose a pedir aprobación humana sólo cuando la reserva lo amerita.

1 · Mapa de arquitectura

El sistema resuelve dos procesos de negocio distintos que comparten la misma puerta de entrada. La diferencia entre ellos no es cosmética: define quién es dueño del dato.

Decisión central. En los pedidos, la aplicación escribe en Notion y n8n sólo avisa. En las reservas, n8n es quien escribe, porque el estado de una reserva depende de un análisis que ocurre dentro del flujo. Confundir los dos repartos rompe cualquiera de los dos procesos.

2 · Estructuras de datos

Cinco bases en Notion, con relaciones explícitas para que ningún registro quede aislado. Los tipos importan: la API rechaza la escritura si el nombre o el tipo de una propiedad no coincide exactamente.

2.1 · Modelo de datos

Campos de estado. Reservas.Estado es el eje del sistema: Esperando_Aprobacion → Confirmada / Rechazada / Vencida. Es lo que escribe el router, lo que sondea el bucle de aprobación y lo que el encargado modifica a mano para dar su veredicto. Los pedidos usan el suyo: Nuevo → Preparando → Listo → En camino → Entregado.

b · n8n → Anthropic (análisis con RAG)

El cuerpo se arma en un nodo Code, no en una expresión: así puede ejecutarse y probarse como JavaScript común. El system prompt es dinámico — se rearma en cada ejecución con las políticas vigentes. 

{
  "model": "claude-opus-5",
  "max_tokens": 4000,
  "system": "Sos un asistente que evalúa solicitudes de reserva…\n\n
             POLÍTICAS VIGENTES DE ARRECIFE:\n
             - [Menu/Media] Descorche de bebidas propias: …\n
             - [Politica_Reserva/Alta] Mascotas en el salón: …\n
             … 23 políticas recuperadas de Notion",
  "output_config": {
    "effort": "low",
    "format": {                                   // salida estructurada:
      "type": "json_schema",                      // el esquema lo garantiza
      "schema": {
        "type": "object",
        "properties": {
          "requiere_revision_humana": { "type": "boolean" },
          "motivo_revision":          { "type": ["string","null"] },
          "confianza":                { "type": "number" },
          "viola_politica":           { "type": "boolean" },
          "politica_relacionada":     { "type": ["string","null"] }
        },
        "required": ["requiere_revision_humana","motivo_revision",
                     "confianza","viola_politica","politica_relacionada"],
        "additionalProperties": false
      }
    }
  },
  "messages": [{ "role": "user",
                 "content": "Nombre: …\nPersonas: 6\nFecha: …\nComentario: …" }]
}
Mapeo de la respuesta. El JSON no está en content[0].text. El modelo razona antes de responder, así que el primer bloque es de tipo thinking y el texto viene después. Se busca el bloque por tipo: content.find(b => b.type === 'text'). Asumir la posición hacía que el análisis fallara en silencio en todas las ejecuciones.

d · Consulta de ocupación

Se filtra por rango y no por igualdad de fecha. Notion compara en UTC: una reserva de las 21:00 -03:00 queda registrada como el día siguiente en UTC, de modo que { equals: "2028-04-22" } no devuelve ninguna reserva de la cena — y el turno de cena va de 19:30 a 00:00. 

{ "filter": { "and": [
    { "property": "Fecha",  "date":   { "on_or_after": "2028-04-22T00:00:00-03:00" }},
    { "property": "Fecha",  "date":   { "before":      "2028-04-23T00:00:00-03:00" }},
    { "property": "Estado", "select": { "equals": "Confirmada" }}
]}, "page_size": 100 }

3 · Optimización de costos

3.1 · Qué tareas usan IA, y cuáles no

La primera decisión de costo es no usar un modelo donde alcanza el código. El sistema tiene cinco tareas y sólo una llama a un modelo de lenguaje.

TareaResuelta conMotivo
Validar precios, horario y zona de entrega Código determinista Reglas exactas y auditables. Un modelo aquí sería más caro, más lento y menos confiable.
Numerar pedidos y reservasContador atómico en Redis Requiere garantía de unicidad; un modelo no la da.
Detectar duplicadosConsulta a Notion Comparación exacta de teléfono y fecha.
Controlar la capacidad del turnoSuma aritmética El dato existe en la base; no hay nada que interpretar.
Interpretar el comentario del cliente contra 23 políticas Claude Opus 5 Único punto con lenguaje natural ambiguo y consecuencias reales.

3.3 · Matriz de decisión del modelo

ModeloEntrada
USD/MTok		Salida
USD/MTok		 Costo por
reserva		300 reservas
al mes		Veredicto para esta tarea
Claude Opus 55,0025,00 $0,0285$8,55 Elegido. Distingue matices que cambian la decisión.
Claude Sonnet 53,0015,00 $0,0171$5,13 Alternativa razonable. Ahorra $3,42 al mes: no compensa el riesgo.
Claude Haiku 4.51,005,00 $0,0057$1,71 Sólo si el volumen creciera dos órdenes de magnitud.

Por qué el modelo más capaz en la tarea más barata. El costo total del componente de IA es de unos 8,55 USD al mes con 300 reservas. Bajar a Haiku ahorraría 6,84 USD mensuales: menos de lo que cuesta un plato de la carta. Contra eso, un error de clasificación tiene consecuencias físicas — confirmar automáticamente una mesa que trae una mascota al salón, o no advertir una alergia grave, se paga con el cliente sentado en el restaurante.

La diferencia se observó en producción. Ante el comentario «cumpleaños, llevamos nuestra torta y una botella de champagne, viene mi perro», el modelo separó lo permitido de lo prohibido citando las políticas por nombre: la torta externa está permitida, el descorche no, y el perro se acepta en la terraza pero no en el salón. Esa granularidad es exactamente lo que los modelos más chicos aplanan.

3.4 · Optimizaciones aplicadas y descartadas

TécnicaEstadoJustificación
effort: lowAplicada Clasificar contra 23 políticas no exige razonamiento profundo. Reduce tokens de salida y latencia.
Tope de max_tokensAplicada — 4.000 Techo ante una respuesta anómala. No puede ser menor: el razonamiento sale del mismo presupuesto y con 1.000 la respuesta se cortaba.
Salida estructuradaAplicada Elimina los reintentos por JSON mal formado, que se pagan dos veces.
Filtrar políticas antes del promptAplicada Sólo entran las marcadas Activo. Las inactivas no se pagan.
Caché de promptEvaluada, no aplicada El bloque de políticas es estable y supera el mínimo cacheable, pero las reservas llegan espaciadas y la ventana por defecto es de 5 minutos: casi todas las lecturas serían fallos de caché. Se vuelve rentable con TTL de una hora si el volumen sube.
API de lotes (50 % de descuento)Descartada Incompatible con el caso: el cliente espera respuesta en el momento y el encargado necesita el aviso al instante.

4 · Seguridad y resiliencia

4.1 · Minimización de datos

DatoSe recogeLlega al modeloSe conserva
NombresísíNotion
TeléfonosínoNotion
EmailopcionalnoNotion
Fecha, hora, personas, zonasísíNotion
Comentario libreopcionalsíNotion

El teléfono y el email no se envían al modelo: no aportan nada a la clasificación y son los datos más sensibles del conjunto. El registro de errores guarda un subconjunto todavía menor — número, fecha, personas y comentario — porque para depurar por qué falló un análisis no hace falta saber a quién llamar.

Gestión de credenciales

  • Ningún secreto vive dentro del flujo: el del webhook está en una credencial Header Auth de n8n, y las claves de Notion, Anthropic, Gmail y Telegram en credenciales propias. El JSON que se publica en el repositorio no contiene ninguna.
  • Los identificadores de bases, el plazo de vencimiento y el destinatario de los avisos se leen de variables de entorno con literal de respaldo, en un único nodo Configuración.
  • Del lado de la aplicación, las variables viven en Vercel; el archivo local está excluido del control de versiones.

4.2 · Rutas de error

FalloRespuesta del sistemaQué ve el usuario
Datos incompletos en el formulario HTTP 400 con la lista de campos faltantes, antes de tocar nada Error en el formulario
Fuera del horario de atención o de la zona de reparto HTTP 409 con el motivo Mensaje explicando cuándo o dónde sí se puede
Exceso de solicitudes desde una IP HTTP 429 (20/hora por IP, 500/día global) Aviso de reintentar más tarde
Notion no responde (pedidos) HTTP 502; el pedido no se confirma «No pudimos guardar tu pedido»
n8n no responde (reservas) HTTP 502; la reserva no se confirma «No pudimos guardar tu reserva»
La API de IA falla o devuelve algo inesperado El flujo continúa: la reserva se marca para revisión humana y se escribe una fila en Errores, vinculada a la reserva Nada: su reserva se registró igual
Gmail o Telegram fallan El flujo continúa; la reserva ya está registrada Confirmación por teléfono
Criterio de diseño. Falla ruidosamente lo que compromete el dato: si el registro no se pudo escribir, no se le confirma nada al cliente. Degrada en silencio lo accesorio: si el análisis o el aviso fallan, la reserva igual queda guardada y llega a un humano. Lo que degrada, deja rastro — de ahí la base Errores.

Guardas explícitas

  • Bucle infinito: el sondeo de aprobación se corta a las 4 horas marcando la reserva como Vencida y escalando por Telegram. El plazo es configurable.
  • Comparación de tipos: los routers comparan booleano con booleano y número con número; ningún filtro compara una cadena contra un número.
  • Duplicados: misma fecha y mismo teléfono con reserva ya confirmada se descarta sin crear una segunda.
  • Confianza en el cliente: nula. Los precios se recalculan contra la carta real; un total manipulado desde el navegador se ignora.

4.3 · Punto de validación humana

El sistema se detiene antes de confirmarle una mesa a un cliente cuando se cumple cualquiera de estas condiciones:

CondiciónOrigen
El comentario contradice una política vigenteAnálisis con RAG
Menciona alergias, mascotas, accesibilidad o un eventoAnálisis con RAG
La confianza del análisis es menor a 0,7Umbral del router
Más de 10 personasRegla de operación
La ocupación del turno supera la capacidadCálculo sobre Notion
El análisis de IA no se pudo completarRuta de error

En ese caso la reserva se guarda como Esperando_Aprobacion y el encargado recibe por Telegram el detalle, el motivo y el enlace directo a la ficha. Aprueba o rechaza moviendo un campo en Notion — sin aprender una herramienta nueva. El flujo lo detecta en cinco minutos y recién entonces contacta al cliente.

Por qué evita el «efecto metralleta». Ninguna comunicación con el cliente final ocurre en la rama de revisión hasta que un humano decide. El aviso al encargado no es una acción sobre el cliente: es la pregunta.

  • n8n/reservas/*.js — código de cada nodo, como archivos ejecutables y probables

  • n8n/RESERVAS.md — decisiones de implementación y sus motivos
Sobre el modo de fallo dominante. Los defectos más costosos del desarrollo no fueron caídas: fueron ejecuciones que n8n reportaba como exitosas haciendo menos de lo que declaraban. El análisis corría sin políticas, la ocupación se calculaba siempre en cero, el correo de confirmación nunca salía. Ninguno encendió una alarma. Por eso el sistema hoy registra cuántas políticas consultó cada análisis y deja constancia en Errores cuando degrada: la resiliencia sin observabilidad sólo esconde el problema.
